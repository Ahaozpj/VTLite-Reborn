# Как публикуются версии VTLite Reborn

Публичный репозиторий содержит документацию, историю изменений и **готовые APK только в GitHub Releases**. Секреты подписи, токены авторизации и приватные данные нельзя загружать ни в репозиторий, ни во вложения.


## Как принимается решение о выпуске

Публикуются **не все собранные APK**. Решение о следующем выпуске принимается по фактическим проверкам; тестовые подписанные файлы остаются в приватном исследовательском хранилище.

- **Лабораторная QA:** APK для внутренних проверок; в публичный GitHub Releases не попадает.
- **Pre-release:** есть подтверждённая работа основных функций на реальном Android, контроль подписи и SHA-256, известные ограничения указаны в заметках; нужна осторожность при установке.
- **Stable release:** проверки обновления, авторизации и сохранения сессии, открытия переписок, отправки текста/медиа и повторного запуска; значимые регрессии отсутствуют. При изменениях токенов отдельно проверяется восстановление и честно описывается риск повторного входа.

Отдельный успешный скриншот функции или прохождение проверки подписи **не является достаточным основанием для нового публичного релиза**. Существующие подтверждённые Assets сохраняются; незащищённые QA-сборки, ключи подписи и приватные данные в релизы не выгружаются.

## Автоматизированная публикация

Рабочий процесс [`publish-verified-apk.yml`](.github/workflows/publish-verified-apk.yml) читает описание будущей сборки из [`releases/latest.json`](releases/latest.json):

1. Загружает APK из **общедоступной** Google Drive ссылки (по ID файла).
2. Сверяет **точный размер и SHA-256** — при расхождении ничего не публикует.
3. Проверяет структуру ZIP/APK.
4. Открывает существующий черновик Release по тегу либо создаёт новый.
5. Прикрепляет APK к **Assets**, не заменяя другой бинарный файл без проверки.
6. Публикует предварительный Release с заметками из соответствующего файла `releases/CPxxx.md`.
7. Проверяет статус выпуска.

Данные личных Google Drive и GitHub аккаунтов, кроме публичного ID файла, в workflow не используются. Запуск выполняется стандартным GitHub Actions токеном с правом `contents: write` только во время выполнения.

## Для следующих версий

1. Получить подтверждение реальной работоспособности новой сборки.
2. Проверить APK, `versionCode`, подпись, размер и SHA-256.
3. Создать новый файл `releases/CPxxx.md` с отдельным разделом **изменения против предыдущей сборки**; внести выпуск в `CHANGELOG.md`.
4. Последним шагом обновить [`releases/latest.json`](releases/latest.json), указав новый тег, имя, публичный Drive file ID, размер и SHA-256. Коммит запускает автоматизацию.
5. Проверить, что в GitHub Releases появился **публичный Asset**, а не только исходный архив.
6. Не удалять проверенные старые APK — они нужны для отката.

**Важно:** если публичная ссылка Google Drive перестанет работать или хеш изменится, workflow завершится ошибкой **без публикации неверной сборки**. Если он не выполнился, используйте ручную загрузку APK в существующий черновик GitHub Release с последующей проверкой SHA-256.


## Обязательный стиль описаний будущих релизов и копируемого анонса

**Долгосрочная просьба владельца проекта:** при **каждом публичном релизе** присылать в чат **короткий, красивый, полностью готовый к копированию русский список изменений относительно непосредственно предыдущего ПУБЛИЧНОГО релиза**. Это обязательный дополнительный результат публикации, а не просьба, о которой нужно спрашивать снова.

Формат будущих выпусков:
1. **Копируемый анонс в чате:** короткий заголовок `🚀 VTLite Reborn vXXXX`, 3–6 коротких пунктов с уместными эмодзи, человеческие формулировки (что стало лучше пользователю), ссылка на релиз и лаконичная заметка об открытой проблеме/предварительном статусе. Не вставлять внутренние CP, Smali/DEX и технические имена без необходимости. Использовать самостоятельный блок текста, который можно копировать целиком без редактирования; не обещать неподтверждённых исправлений.
2. **Репозиторий:** сохранять этот анонс в `releases/CPXXX_SHORT.md`, отдельно от детальных заметок.
3. **Страница GitHub Release и `releases/CPXXX.md`:** сверху привлекательный, простой и понятный любому пользователю заголовок, раздел `✨ Что нового по сравнению с vXXXX`, 3–6 коротких пунктов, кнопка-ссылка на установочный APK, `⚠️ Известные проблемы`, инструкция обновления. **После** короткого объяснения — развёрнутая техническая часть, предпочтительно внутри сворачиваемого блока GitHub Markdown `<details><summary>🔧 Технические подробности</summary> ... </details>`.
4. Сравнивать **с последним опубликованным GitHub Release**, а не с последней промежуточной приватной QA-сборкой. Чётко разделять подтверждённые полевые исправления, изменения кода без полевой проверки и запланированные функции. Если изменений мало, честно написать об одном важном исправлении, не выдумывать дополнительные.
5. После записи заметок в GitHub **обновить фактический текст опубликованной карточки Release**, а не только файл `releases/CPXXX.md`. Использовать проверенный workflow, сверить что Asset не был изменён или заменён, SHA и размер совпали, а предыдущие выпуски сохранены.

Пример копируемого формата: [анонс CP309](releases/CP309_SHORT.md). Перед финальным ответом проверить, что обе версии (короткая и подробная) реально сохранены и что опубликованный GitHub Release показывает обновлённое понятное описание.


## Обязательная публикация исходников каждого публичного релиза

Постоянное требование владельца от 26.11.2026: при каждом публичном релизе (включая pre-release) одновременно готовить и публиковать соответствующие именно этому APK исходники собственных изменений Reborn в публичном репозитории. Приватный VTLite-Reborn-Dev не открывать.

- Хранить проверенный снимок собственных исходников/патчей в `source/releases/v<versionCode>-cp<CP>/`; добавлять в заметки релиза прямую ссылку на него и, по возможности, отдельный архив Source в Assets. Не считать автоматически генерируемый GitHub Source code.zip доказательством наличия исходников приложения.
- Зафиксировать точные исходные ревизии, базовую версию, инструменты, патчи, инструкции сборки, SHA-256 исходного архива и соответствующего APK. Не обещать побайтовую воспроизводимость, пока она не проверена.
- Проверять происхождение и права на каждый публикуемый компонент. Публичная доступность чужого кода не означает разрешение на его повторное распространение. Не копировать декомпилированный VK, сторонние библиотеки или ресурсы без установленного разрешения; при необходимости публиковать только собственные разрешённые изменения и описание внешних зависимостей. Не называть неполный комплект полными исходниками.
- Перед публикацией проверить содержимое на ключи подписи, keystore, пароли, токены, cookies, идентификаторы аккаунтов, журналы, персональные данные, внутренние ссылки и иные секреты. Не публиковать приватные архивы целиком. Подписывать пользовательские сборки прежним закрытым ключом; инструкции самостоятельной сборки используют отдельный ключ.
- Новый релиз не считать завершённым до проверки доступности исходников и ссылки из Release. Если права, соответствие или безопасность не подтверждены, отложить публичную публикацию соответствующего материала и явно сообщить владельцу о препятствии. Не подменять ранее опубликованные APK.
- Начальный ретроспективный выпуск исходников: v4954-cp584. Опубликован [проверенный частичный комплект](source/releases/v4954-cp584/README.md): девять проверенных Smali-классов и скрипты упаковки, отчёт сопоставления оригинала и релиза. Полный накопленный комплект пока не подтверждён.

### Полный комплект и стандартные архивы GitHub

Уточнение владельца от 26.11.2026: целевой результат — полный комплект исходников всех собственных изменений Reborn, необходимых патчей, сборочных сценариев и разрешённых к распространению зависимостей для каждого публичного релиза, а не только изменения последнего CP. Непубликуемые сторонние компоненты указывать как внешние входы с точными версиями/хешами и инструкцией получения из законного источника. Не называть такой комплект полными исходниками всего клиента VK.

До создания нового релизного тега подготовить и проверить публичный снимок исходников именно выпускаемой версии. Создавать тег на проверенном коммите с этим снимком, проверять, что стандартные GitHub Source code (zip) и Source code (tar.gz) действительно его содержат. По возможности независимо проверить сборку с чистого окружения и собственным тестовым ключом. Существующие опубликованные теги не перемещать: для ретроспективного комплекта использовать отдельный неизменяемый тег исходников и ссылку/архив в существующем релизе. Для v4954 пока опубликован лишь частичный комплект на main; не заявлять, что архивы исходного тега уже содержат его.

### Уточнение границ публикации: только собственные изменения Reborn

Окончательное решение владельца 26.11.2026: публиковать полный накопленный набор собственных изменений VTLite Reborn с начала разработки до соответствующего релиза, не только дельту последнего CP. Не зеркалировать исходный VTLite, декомпилированный VK, их ресурсы и сторонние бинарники. База — отдельно получаемая законным способом зависимость, с точной версией и SHA-256. Для унаследованных классов хранить только собственные изменения в виде проверенных патчей/сценариев преобразования, без копирования неизменённого чужого кода. Проверять происхождение даже новых классов, ресурсы, права на публикацию патчей и отсутствие секретов; это не гарантия отсутствия иных правовых ограничений. Проверять применение к чистой базе и соответствие выпущенному APK. Стандартные архивы ZIP/TAR.GZ должны содержать полный проверенный комплект собственных изменений на релизном теге; для уже выпущенного v4954 использовать отдельный тег исходников, не перемещая исходный тег. Частичный комплект обозначать явно до завершения восстановления и проверки.

Текущий статус ретроспективного v4954: опубликованы 14 проверенных собственных Smali-классов, сценарии точного восстановления 90 из 167 выявленных изменённых унаследованных классов, отчёт и контрольные суммы. Полный комплект и ZIP/TAR.GZ пока не готовы; продолжить проверку оставшихся 77 классов, 99 кандидатов новых классов, зависимостей и ресурсов. Приоритет владельца: сначала завершить исходники, затем кнопка диагностики CP602–CP603, затем восстановление всего функционала оригинального VTLite и расширение Reborn.
